Why move

Streamlit re-runs the whole script on every interaction, serves one session at a time per worker, and on the hosted tier it sleeps when idle — so the first visit each morning is a cold start and every filter change is a full recompute. The data work underneath is fine; the delivery layer is the bottleneck.

The target splits the two. A FastAPI process holds the Python logic as plain service functions behind JSON endpoints and stays warm on an always-on host. A React app renders the UI, caches responses on the client, and keeps filter state in the URL so views are finally shareable. Supabase — the stack already in use elsewhere — becomes the Postgres database, the auth provider, and file storage. The scheduled extraction and sync jobs do not change.

The phased plan

Six phases, run in order. Streamlit stays live and in use the whole time — pages move over one at a time, and there is no flag day. Estimates assume one developer working part-time.

0

Supabase cutover & service layer

Prove Supabase with the app you already have; separate the Python logic from Streamlit.

3–5 days
  • Create the Supabase project — same region as your users; enable pg_cron.
  • Move the data — pg_dump from Neon, restore into Supabase, verify count(*) on every table.
  • Repoint everything at Supabase — .streamlit/secrets.toml and the three Actions DATABASE_URL secrets. App uses the transaction pooler (6543); the pipeline scripts use the session connection (5432).
  • Regression pass on Streamlit — run the dashboard, one Gmail extraction, and one QBO sync against Supabase. Nothing should change.
  • Extract the service layer — move data.py's query + transform functions into backend/services/; leave a re-export shim so Streamlit still imports them.

Exit when Streamlit runs unchanged on Supabase, all scheduled jobs pass a run, and the logic modules import with no streamlit dependency.

1

Skeleton, auth & first deploy

The full stack stands up in production with one real page.

~1 week
  • FastAPI app — /health, JWT middleware verifying Supabase tokens against its JWKS, a connection pool (psycopg_pool).
  • Supabase Auth — create the team's accounts (email allowlist). All data access stays server-side through FastAPI with the service role, so no row-level-security policies are needed yet.
  • React shell — Vite + TS, Mantine, router, TanStack Query, a Supabase auth provider, protected routes, a filter bar bound to the URL query string.
  • Port the Overview page — one or two endpoints returning the KPI numbers + data series; render with a first-pass ECharts treatment (the full shared theme lands in Phase 2).
  • Deploy — FastAPI to Railway (Dockerfile build, always on), the SPA to Cloudflare Pages; wire CORS and the API base URL.
  • Move the OAuth callbacks — add /auth/gmail/callback and /auth/qbo/callback FastAPI routes; register the new redirect URIs in Google Cloud Console and the Intuit app (keep the Streamlit ones during overlap).

Exit when a teammate logs in at the production URL, sees the live Overview page, and it loads in under a second warm.

2

Read-only analytics pages

Every page you only look at is now in the new app — on a proper chart layer.

~2.5 weeks
  • Build the chart layer first — the ECharts theme module (palette, gridlines, legend, numerals, axis type) and the <Chart> / <KpiCard> / <DataGrid> / scope-bar wrappers. This is the design investment; ~3–4 days, then every page is fast.
  • Port in order — Customer 360, Products & Sizes, Explore, Order Lifecycle. Roughly half a day to a day each once the chart layer exists.
  • One endpoint pattern — GET /api/<page>?start=&end=&customers=&products=&sizes=, stateless, returns records + data series. The backend assembles the shared filtered context once per request.
  • Client caching — TanStack Query staleTime tuned per endpoint; stale-while-revalidate so re-visits are instant.

Exit when the four analytics pages match the Streamlit output number-for-number, every chart is drawn through the shared theme, and pages load from cache instantly on return visits.

3

Interactive & editing pages

The pages where people click things — the real work of the rebuild.

~1.5 weeks
  • Match & Reconcile — confirm / reject links; wrap qbo_matcher.run_matching and the confirm calls as POST endpoints.
  • Data Quality & Extraction Review — the review queue, the verdict form, the seeded-modification flow; Supabase Realtime can live-update the queue as the pipeline writes new flags.
  • Editable grids — Edit PO, Reference Prices, the review line-item editor. AG Grid + optimistic mutations; the existing save_po_edit / save_extraction_review / price functions become POST handlers unchanged.
  • Settings & Connections — QBO / Gmail connect + disconnect, sync buttons, product hiding, saved views.

Exit when every Streamlit page has an equivalent in the new app and a full day's real work can be done without opening Streamlit.

4

Cut over & retire Streamlit

The new app is the app.

2–3 days
  • Parallel run — the team uses the new app for one to two weeks; Streamlit stays reachable as a fallback.
  • Drop the old redirect URIs — remove the Streamlit OAuth callbacks from Google and Intuit once nothing points at them.
  • Delete dashboard/ — it lives on in git history; update AGENTS.md and the README.

Exit when the Streamlit deployment is turned off and no one has asked for it back.

5

Harden for speed

Take the wins that only make sense once the shape is settled.

3–5 days
  • Materialized views — the revenue / product-mix / customer rollups become materialized views, refreshed by pg_cron or a step in the scheduled jobs. Expensive dashboard queries become instant reads.
  • Response compression & cache headers — brotli/gzip on the API; Cache-Control on stable endpoints; the SPA already sits on a CDN.
  • Observability — Sentry for errors, an uptime check on /health, Railway metrics.
  • Decide on scale — one Railway instance is plenty for an internal tool; if you add a second for redundancy, move the server-side TTL cache to Supabase or Redis.

Exit when every page is under ~400 ms warm and an error surfaces in Sentry before a user reports it.

Cross-cutting concerns

Auth
Supabase Auth issues the session; the SPA sends the JWT as a bearer token; FastAPI verifies it against Supabase's JWKS. All Postgres access is server-side with the service role, so no RLS policies are required — simpler, and the frontend never touches the database directly.
Database connections
API uses the transaction pooler (:6543) — many short queries, kept warm in a psycopg_pool. The pipeline scripts use the session connection (:5432) — they need long transactions and execute_values batches. This also ends the SSL connection has been closed unexpectedly failures the Neon autosuspend caused.
Charts & visual polish
Charts are a deliberate design investment, not a straight port. The backend returns plain data series (labels, values, group keys); the client draws them with ECharts (echarts-for-react, tree-shaken — smooth, refined defaults, a fraction of Plotly's weight) for KPI sparklines too; KPI cards themselves are Mantine (Tremor needs Tailwind, which fights Mantine). The house colour-blind-safe palette and the style() rules — one hairline gridline set, no tick marks, top-strip legend, tabular numerals, muted axis labels — become a single ECharts theme module plus a <Chart> / <KpiCard> wrapper, built once in Phase 2 and reused by every page. Reusing Plotly via react-plotly.js stays available as a faster fallback if the schedule tightens.
Filters & state
A React filter bar writes to the URL query string; endpoints are stateless and take the filters as params. Views become shareable links — a long-standing Streamlit gap.
Scheduled jobs
Unchanged. extract_pos.yml, qbo_sync.yml, and eval_extraction.yml keep running on GitHub Actions; only DATABASE_URL moves to the Supabase session string.
Secrets
Backend (Railway variables): DATABASE_URL + SUPABASE_URL (token verification via the JWKS endpoint; SUPABASE_JWT_SECRET only if the project still signs HS256), ALLOWED_ORIGINS + FRONTEND_BASE, and GMAIL_* / QBO_* for the connect flows. The API never calls Claude. Frontend (build-time, public-safe): VITE_SUPABASE_URL, VITE_SUPABASE_PUBLISHABLE_KEY (or legacy VITE_SUPABASE_ANON_KEY), VITE_API_BASE.
PDF storage (optional)
The pipeline never keeps PDF bytes today. If you want attachments viewable in the app, push them to a Supabase Storage bucket during extraction and store the object path on the PO row.

Risks & decisions

Risk / decisionHow it's handled
pandas in the request path could block Endpoints stay sync — FastAPI runs them on a threadpool. Anything over ~300 ms goes behind a TTL cache or a materialized view (Phase 5).
Supabase transaction pooler drops session features Documented split: pipeline scripts on :5432, the API on :6543. Decided in Phase 0.
Nine pages is still a lot of UI to rebuild Strangler-fig. Streamlit stays live; pages move one at a time; the team can switch per-page. No big-bang cutover.
Charts must look genuinely professional, not ported ECharts + Mantine with a single shared theme built up-front in Phase 2 (~3–4 days). Costs more than piping Plotly figure dicts, but it's the reason the charts look considered rather than default.
Editable grids are the hardest part Deferred to Phase 3, after the pattern is proven on read-only pages. The existing save_* functions are reused verbatim as POST handlers.
OAuth redirect URI mismatch after the move New callback URLs registered before switching; Streamlit's callbacks kept working through the overlap; old URIs removed only in Phase 4.
Data drift during the DB move Move first (Phase 0) with Streamlit pointed at Supabase and verified by row count. No dual-write window — one clean switch.
Solo developer, no deadline → risk of stalling mid-migration Each phase leaves a working, shippable state. Stopping after Phase 2 still gives an always-on app for all the read-only work.
